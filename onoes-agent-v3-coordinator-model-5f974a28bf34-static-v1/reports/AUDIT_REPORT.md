## 6. Nonblocking Findings

- ID: M-1 — composite-envelope allocation ordering is asserted in prose but not exercised
- Severity: low (model completeness; contract already states the correct rule)
- File/symbol/line: `tests/tests/helpers/candidate-v3-coordinator-model.ts` lines 28–31 (`bounded`), 157 (`bounded(inventoryWire)`, `bounded(checkpointWire)`), 167–169 (`bounded(wire({…}))`), 118–119 (bootstrap request composition); `ONOES_AGENT_V3_WORKER_MESSAGE_DESIGN.md` "Numeric ceilings", sentence "Both inner and outer caps apply, so available envelope space cannot increase an inner limit. Encoding must reject before exceeding the envelope."
- Observed fact: `MODEL_LIMITS.wireBytes` (262,144) is applied to each inner string and again to the composed envelope, with no inner-budget check before composition. Two 200 KiB inputs each pass the inner bound, and the model then materialises a ~410 KiB envelope string before rejecting it. The same ordering applies to the bootstrap request, which composes metadata + inventory + history wires and only then bounds the result. The existing bound test (test 22, line 263) uses a single oversized input, so it exercises the inner cap only; no case asserts that composition does not occur when the inner sum exceeds the envelope budget.
- Why it matters: the physical contract's stated rule is exactly the one the executable model cannot falsify. A harness or adapter author reading the model would reproduce the compose-then-check ordering, which is the allocation-before-cap hazard the design set out to forbid.
- Reproduction/probe: static reading plus arithmetic on `MODEL_LIMITS`. NOT RUN.
- Required correction: in the model, check `Buffer.byteLength(inventory) + Buffer.byteLength(cp) + fixedEnvelopeOverhead <= MODEL_LIMITS.wireBytes` before building the request wire (and the three-wire equivalent for bootstrap), and add a test asserting `counts.worker === 0` for inputs that individually pass but jointly exceed.
- Status: new.

- ID: M-2 — failed bootstrap leaves no latch and no attempt accounting
- Severity: low
- File/symbol/line: `candidate-v3-coordinator-model.ts` lines 108–131 (constructor, `#closeBootstrap`), line 91 (`counts`), line 94 (`retire`); test assertions at lines 109–110 and 126 (`ownerHeld === false`, `bootstraps === 0`); `ONOES_AGENT_V3_WORKER_MESSAGE_DESIGN.md` lifetime table row "Uninitialized".
- Observed fact: post-staging faults latch correctly — `#close()` leaves `world.ownerHeld === true`, and the tests confirm re-instantiation then throws. Bootstrap-phase faults do not: a rejected bootstrap reply, epoch/anchor/deadline/metadata drift during bootstrap, an oversized bootstrap response or a bad lifetime counter all invalidate T and throw while leaving `ownerHeld === false`, and `counts.bootstraps` increments only on success. An unlimited number of fresh `new Coordinator(world)` attempts is therefore permitted, and failed attempts are recorded nowhere.
- Why it matters: no write occurs, so this is not a correctness defect, and design §3 does permit Uninitialized → fresh bootstrap. But against an untrusted reply channel the physical contract bounds nothing, and the harness has no counter with which to assert that it should. C08's accounting assertions can only compare counters that exist.
- Reproduction/probe: static. NOT RUN.
- Required correction: add `bootstrapAttempts` to the model's counters (incremented before the reply is parsed) and state a bounded attempt/backoff rule for the Uninitialized row of the message-design lifetime table.
- Status: new.

- ID: M-3 — the in-transaction preflight omits the local/anchor stream relation
- Severity: low (scope precision, not a defect)
- File/symbol/line: `candidate-v3-coordinator-model.ts` lines 192 (pre-transaction `w.anchor !== this.#s.history`), 195–202 (transaction block: `schemaValid` and pre-identity only), 206–208 (post-commit `relation !== "one-ahead-claims"`), 210; `ONOES_AGENT_V3_COORDINATOR_PAIR_DESIGN.md` §4 step 5 ("Do not call worker, anchor, consent or task callbacks here") and C13 ("At bootstrap and each append boundary").
- Observed fact: inside the simulated transaction the model rechecks schema validity and the complete pre-state identity, but not the stream relation. An anchor advance concurrent with the transaction is caught only after the local commit, by the post-commit relation check, which closes the owner. This is consistent with the design — no anchor contact inside a transaction is mandated, and the transactional identity does cover the unconfirmed tail as C13 requires.
- Why it matters: C13 coverage should not be over-claimed. The model demonstrates the stream comparison at the bootstrap, pre-transaction and post-commit boundaries; it does not and cannot demonstrate a pre-write deny for anchor drift, because the design forbids the contact that would detect it. A reader of the controls table could mistake "C10 / C13 … transaction identity covers the local tail" for a stronger claim.
- Reproduction/probe: static. NOT RUN.
- Required correction: state in `ONOES_AGENT_V3_COORDINATOR_MODEL.md` that the anchor relation is evaluated at the bootstrap, pre-transaction and post-commit boundaries only, and that mid-transaction anchor drift is by construction a post-commit close rather than a pre-write denial.

- Severity: medium (capacity definition; the design itself makes this a gate)

- Observed fact: the per-row member caps sum to 32,768 + 8,192 + 4,096 = 45,056 bytes. At the 1,000-operation ceiling that is 45,056,000 bytes of member content before the envelope escapes each member as a JSON string. Under the worst-case expansion the caps themselves permit (every byte an escaped character, ×2) a fully loaded 1,000-row inventory needs roughly 86 MiB against a 64 MiB envelope cap. The binding constraint is therefore the 64 MiB inventory cap, not the advertised 1,000-operation ceiling, and the maximum jointly admissible per-row size is stated nowhere. The retained-history side is coherent by contrast: 7,001 × 4,096 = 27.35 MiB raw, at most 54.7 MiB escaped, about 14.5% under the 64 MiB cap. The outer envelope caps are also coherent — bootstrap 256 MiB + 64 KiB against an inner sum of 128 MiB, append 128 MiB + 64 KiB against a 64 MiB inventory — each exactly double plus 64 KiB of fixed-field headroom.
- Why it matters: `ONOES_AGENT_V3_WORKER_MESSAGE_DESIGN.md` states that if maximum-history workloads cannot fit these limits the gate fails and capacity must not be silently lowered. The capacity probe cannot detect this: its corpus averages 6,819 bytes per row, about 10.4% of the inventory cap, so it exercises the operation ceiling at roughly a tenth of the byte ceiling.
- Reproduction/probe: arithmetic on the parser constants and the probe's reported `inputBytes`, performed offline. No subject execution.
- Required correction: state the assumed encoding-expansion factor and the maximum jointly admissible per-row size at 1,000 operations, or raise the inventory envelope cap so the two ceilings are jointly reachable; and specify that the C12 maximum-history corpus must use maximum-size rows, not average-size rows.
- Status: new.

## 8. Security and Integrity Review

- Secrets: none observed. `SANITIZATION.json` correctly calls itself a configured tripwire and disclaims proof of absence.
- Injection/control content: the parser boundary is primitive-only and canonical. `parse()` bounds by length and byte length before `JSON.parse`, then requires `canonicalJson(value) === text`, so alternate serialisation, duplicate or unknown fields (`.strict()`), BOM prefixes and trailing frames are rejected — test 8 exercises `"\uFEFF"+reply`, `reply+"\n"`, `"{}"` and an over-cap string against both request parsers, and asserts through a reflecting `Proxy` that no caller getter or `ownKeys` trap is ever invoked. Errors are normalised to `ModelDenied("synthetic-pair-closed")`; test 18's `throwAt` cuts raise a raw `Error("synthetic crash: must not escape")` and the suite asserts only `ModelDenied` escapes, so no raw message, path or rejected input crosses the boundary.
- Authorization/admission: none in scope, and the model adds none. T is private with no externally callable method; C is built from bounded primitive strings; `snapshot()` is used only to read the pre-head for comparison, never to recover S. No result field says authorised, safe or stopped.
- Message binding: the append response must echo domain, operation, lifetime, request number, nonce, epoch, deadline, pre-identity, input and checkpoint digests, must carry `requestDigest === rawDigest(requestWire)`, and must carry `resultDigest === hash(core)`. Test 5 rehashes each of thirteen fields — including `extra` for unknown-field injection and a `v2` domain — and every case denies with `transactions === 0` and `anchorAttempts === 0`. Test 16 replays a previously valid response against the next staged request and it is denied. Bootstrap is request number 0 in a separate domain with its own thirteen-field binding test, and a stale bootstrap reply from a retired lifetime is denied while the observed sequence is asserted to be exactly `[0, 1, 2]` within one lifetime.
- Isolation/custody: F, schema validity and settlement are booleans by construction, and the documents say so in three places. `retire()` denies while `activity !== 0`, so modelled unsettled work blocks replacement — tests 13 and 14 hold a gate open, assert `activity === 1`, assert both `retire()` and re-instantiation throw, then release and assert `activity === 0` with `anchorAppends === 0` and `promotions === 0`. Physical P-controls remain untested by anyone.
- Mutation/concurrency: one owner via the `ownerHeld` latch, one in-flight request via the `ready → busy` transition, `queuedRequests: 0`, and reject-not-queue. Test 19 confirms a second client cannot construct and a concurrent append is denied with `worker === 1`, while the winner still promotes. The busy-loser denial is deliberately raised before `#phase = "busy"`, so a loser cannot poison the winner. Cross-process races are outside what an in-process model can establish.
- Provenance: publisher-local Git, publisher-reported product membership, `AUTHOR_REPORTED_NOT_INDEPENDENT`. The packet commit is immutable and every member's bytes are verified against it; no independent bundle or tree authentication exists.

## Focused questions — answers with file/section and controls

1. **D-1/D-2 streams and identities.** Applied as required. `COORDINATOR_PAIR_DESIGN.md` §2 lines 61–75 now state that the ledger persists the complete retained checkpoint stream in the same atomic local transaction, that step 6 appends to the local stream before anchor confirmation leaving an unconfirmed tail, that the authenticated anchor stream is authoritative, that bootstrap fully replays the local stream and requires byte-identical streams or local = full anchor prefix + exactly one tail, that any other relation closes without repair, and that the in-transaction history identity always covers the tail. Lines 45–59 fix the pre-state identity as ⟨sha256(metadataWire), sha256(inventoryTransportWire including every recordWire/settlementWire/checkpointAWire), sha256(checkpointHistoryWire), head.checkpointDigest⟩ with no adapter-selected encoding. `candidate-v3-pair-claims.ts` implements exactly that tuple, with the fourth component taken from the reference parse rather than a raw hash. Complete stream comparison and transaction rechecks **do** cover context-only and unrelated-row drift: `equal`/`oneAhead` are byte comparisons over the whole history wire, and the inventory component hashes the full transport envelope, so an optional A context appearing or disappearing changes the identity even at constant row count. Model tests 3 and 4 confirm this for metadata, an earlier history checkpoint, a same-count row field change, an added optional context, and a change to a *different already-completed* row while another subject is staged — each denying with `transactions === 1`, `commits === 0`, `anchorAttempts === 0`. Test 20's "matching head cannot conceal a changed earlier anchor checkpoint" closes the head-only shortcut.
2. **T advance then reuse.** No. Every path after staging funnels into `catch { this.#close(); return deny(); }`, which invalidates T and sets phase `closed` permanently, and `#close()` does not release the world's owner latch, so re-instantiation also denies. Verified across: no-write rejection (test 2, and the owner stays closed on a later valid request with `worker` still 1), commit loss and malformed read-back (test 12's six cuts and test 15's read-back corruption, `commits === 1`, `promotions === 0`, `confirmed` unchanged), lost anchor reply (test 15's `anchor-committed` reversion, `anchorAttempts === 1`, `promotions === 0`), epoch and head drift after settlement (test 10, `transactions === 0`), fence/policy loss (`#live`), clock regression (test 22), deadline expiry and abort (tests 13 and 14). Private S promotion happens only at line 226 after exact read-back, exact acknowledgment and all live checks, and is immediately followed by a close if forward policy is gone. Attempt accounting is present and asserted (`worker`, `transactions`, `commits`, `readBacks`, `anchorAttempts`, `anchorAppends`, `promotions`), with `anchorAttempts` incremented before contact. No compensation, no repeat, no queue — `queuedRequests: 0` and the busy path denies rather than enqueueing. The one accounting gap is M-2: failed bootstraps are not counted and do not latch.
3. **D-3 schemas and phase bypass.** Both canonical schemas are present and strict. Bootstrap: `synthetic-v3-bootstrap-request/v1` / `-response/v1`, `operation: "bootstrap"`, `requestNumber: z.literal(0)`, with metadata/inventory/history digests each required to equal `rawDigest` of the corresponding wire, and the response echoing every `bootstrapCommon` key plus `requestDigest` and `post`. Append: `requestNumber` positive safe integer, fresh nonce, epoch, four-element pre-identity, input and checkpoint digests each bound to their wire, absolute deadline, and a response carrying full echo plus `post` and `resultDigest = hash(core)`. No, none of the four bypasses works: a correctly rehashed stale or mismatched reply fails on `requestDigest` and the field-by-field echo (test 5, thirteen fields; test 16, a genuinely valid older response); bootstrap replacement fails because `bootstrapCommon` includes lifetime and epoch and the constructor additionally re-verifies `post`, deadline, live epoch, fence, schema, local identity and anchor digest after the reply (test 7, including a stale retired-lifetime reply and four drift variants, all with `ownerHeld === false`); a duplicate request cannot exist because exactly one may be in flight; and the counter edge is guarded by `if (this.#requestNumber >= Number.MAX_SAFE_INTEGER) return deny()` before increment, with `lifetimeCounter` rejected for NaN, Infinity, −1 and MAX_SAFE_INTEGER (test 23). Gaps between model and proposed physical contract: binary transport and UTF-8 decoding, authenticated IPC and peer identity, MAC-versus-digest (the design correctly notes a length field or request digest is not a MAC), shared monotonic clock conversion across processes, secure nonce generation (the model's UUID counter is deterministic and says so), and the M-1 composition-ordering rule.

6. **Honesty of the four distinctions.** Yes, and the separation is visible in code rather than only prose. Stale activity cannot become a production permission: `retire()` is the only release, it denies while activity is outstanding, and the model document, the design and the message design each state that it is not authenticated fencing and that losing the IPC channel is not a stop witness. 7. **Revocation after local commit.** Yes, bounded correctly. After the commit the live checks switch from the policy predicate to the settlement predicate (`#live(deadline, false)`), so only pre-reserved settlement authority can carry the already-committed exact payload to the anchor; the deadline is never reset and the epoch, fence and owner checks all still apply at every seam. At promotion, `if (!w.policy) { this.#close(); return; }` grants no renewed forward readiness. The structural bound is `7 * CANDIDATE_V3_MAX_OPERATIONS + 1 = 7,001` with `min(1)` forcing genesis, so 6,001 versus 7,001 is a gap of exactly 1,000 — one further per-operation event round across all operations — and the probe reaches 85.7% of the checkpoint ceiling while filling the operation ceiling completely.

## Identity and framing

A future pinned worker belongs to one coordinator lifetime/current owner epoch.
Host selection of that executable, private IPC, physical fencing, trustworthy
request settlement and descendant termination are separate mandatory gates.
Only primitive canonical UTF-8 JSON messages enter the parser. Reject BOM,
duplicate or unknown fields, alternative serialization, invalid UTF-8, trailing
frames and over-limit bytes before parsing or copying. Bound both the advertised
length and bytes actually received. A length field or request digest is not a MAC.
No paths, commands, environment values, task callbacks or real approval objects
are carried. No result says `authorized`, `safeToExecute` or `processStopped`.

The proposed single-flight append request contains exactly:

- domain/version and operation `append`;
- lifetime ID and monotonically increasing request number (no wrapping), plus a
  fresh host-generated 128-bit random nonce, never generated by task input;
- current authenticated owner epoch as an envelope binding, NOT a rewrite of
  historical row owner generations;
- four-element pre-identity: SHA-256 of exact existing canonical metadata,
  inventory transport, retained local checkpoint history, and the head digest;
- complete candidate inventory wire and checkpoint wire, each with SHA-256 of
  its exact UTF-8 bytes (no JSON-string wrapping before hashing);
- one absolute monotonic deadline in the lifetime's host clock domain.

The request digest hashes the canonical complete request. The response echoes
domain/version/operation, lifetime/request number/nonce, owner epoch, complete
pre-identity, input/checkpoint digests, original deadline and request digest. It
adds the four-element post-identity and a result digest over the complete response
core excluding that digest. Response limits and canonical equality apply before
any comparison. Every echo must match the private pending request; a correctly
rehashed response for another request still fails. Worker-reported times never
extend the host deadline. Shared monotonic clock conversion must be fixed and
tested before physical implementation; raw clock values from unrelated processes
are not assumed comparable.

Bootstrap is a separate operation accepted only in Uninitialized: exact enrolled
metadata, complete inventory/history wires, current epoch, independently discovered
anchor stream identity, lifetime/request number/nonce/deadline. Full replay is
mandatory; no cached-summary or serialized-T import is defined. The coordinator
compares the full authenticated anchor stream itself; the worker cannot certify
that caller-supplied discovery is authentic. Bootstrap response echoes all request
bindings and the reconstructed identity/summary. Error output is a fixed bounded
failure code with request binding, never rejected input, paths or raw exceptions.

The harness now tests primitive canonical bootstrap and append envelopes,
operation/lifetime/request-number/nonce/epoch echoes, all input identities,
request/result digests, pre/post identity, deadline and strict version. Bootstrap
is request zero; appends increase within that lifetime. Responses have a separate
16 KiB cap. A stale bootstrap reply, rehashed wrong identity or bootstrap-state
drift cannot create a ready owner. Its deterministic UUID counter is synthetic,
NOT secure nonce generation. Physical binary transport/UTF-8 decoder, shared
clock conversion and authenticated IPC are still not implemented by that helper.

## Lifetime and late-message table

| State | Accepted transition | Denial/stop behavior |
| --- | --- | --- |
| Uninitialized | One full bootstrap under fresh custody/discovery | Any append or summary import closes |
| Ready/confirmed | One append captured from private S before T advances | Busy caller rejects, zero queue; no second T owner |
| Validating | Exactly matching response and independently established request settlement | Mismatch, timeout, abort, worker loss or malformed transport closes |
| Staged/T advanced | Local transaction, read-back, exact anchor append/confirmation | No second worker append while pair is unconfirmed |
| Pair confirmed | Promote S and permit the next request if authority remains current | Revocation may settle the old pair but never grants new task authority |
| Closed | Bounded diagnostics; termination and fresh-owner recovery only | Late/duplicate response discarded; no rewind, retry or replacement from a local reset |

Request completion permits the fixed persistent worker to remain alive. It does
not prove process exit. On close, outstanding activity remains unsettled until
independently confirmed; losing the IPC channel is not a stop witness. Replacement
requires confirmed termination of relevant work, fresh ownership/fencing/discovery
and full replay. The protocol has no message that clears a poisoned lifetime.

Bootstrap-attempt rule (M-2): charge an attempt before parsing or validation and
permit at most one bootstrap per owned lifetime. Any failure consumes that
attempt. Recreating the coordinator object cannot reset the accounting or retry
Uninitialized work. A further attempt requires explicit retirement, all relevant
activity settled, and fresh ownership/discovery under a new epoch; there is no
automatic backoff/retry loop. In the test model this is a private world-owned
latch plus a monotonic bootstrapAttempts counter. Its explicit test-driver
retire() operation is NOT physical fencing or authority to replace a real owner.

## Numeric ceilings selected for review, NOT capacity evidence

Proposed production admission profile: one worker per owned store, one pending
request, **zero queued requests**, one IPC connection, one complete response
(16 KiB maximum). Inner metadata is at most 1,024 bytes; inventory and retained
history each at most 64 MiB; a checkpoint at most 4,096 bytes; 1,000 operations
and at most 7,001 retained checkpoints as already capped by the pure parser.

Bootstrap envelope cap: **256 MiB + 64 KiB**; append envelope cap: **128 MiB +
64 KiB**. These allow JSON re-escaping of the canonical inner strings plus fixed
metadata. Both inner and outer caps apply, so available envelope space cannot
increase an inner limit. Encoding must reject before exceeding the envelope;
streaming bounded transport does not mean unbounded buffering is allowed.

Capacity precision (M-6): independent per-member maxima are rejection limits,
not a promise that their Cartesian product fits. The 64 MiB inventory limit
also applies to the complete canonical encoded envelope. For n nonempty rows,
its exact size is 64 + (n - 1) + sum(encodedRowBytes). At 1,000 rows an equal
allocation is at most 67,107 encoded bytes per row; different row sizes may share
the remaining budget. A row with three non-null empty wire strings costs 58
bytes; a conservative sufficient uniform raw-member sum is 33,524 bytes if
every raw canonical byte expands by at most two. This is budget arithmetic,
not a new restriction on accepted schemas or a supported-capacity reduction.
The independent member maxima sum to 45,056, and that hypothetical worst-case
cross-product would need 90,171,063 bytes including scaffolding: it must reject,
not silently raise the envelope cap. Future encoders must charge actual escaped
row bytes against the remaining aggregate budget before composing the envelope.

This does not prove such maximal strings satisfy the strict inner schemas:
their fixed UUID/digest/time/enum fields and legal history graph impose smaller
constraints. Conversely, the existing dense 6,001-checkpoint probe is not proof
of the worst admissible byte shape. Deriving and testing that bound, maximum
aggregate allocation and physical C12 behavior remain OPEN. No existing parser
constant is raised/lowered and no maximum-byte performance claim is made here.

Absolute budgets proposed for measurement: bootstrap **30 seconds**, ordinary
append/pair **10 seconds** overall with no phase reset, stop confirmation **5
seconds** separately. Expiration denies rather than stretching a lease. A host
watchdog must enforce deadlines while the worker is synchronously validating.
Proposed process budgets: **2 GiB committed memory per validation worker**,
**2 GiB per dedicated coordinator host**, **4 GiB combined**; a separate dashboard
must stay responsive. OS/job enforcement and measured accounting of encoded,
decoded, staged, retained, native and queued memory are prerequisites, not facts
established by these numbers. Do not allocate these amounts on the operator's PC
or alter its limits merely because this design names them.

If maximum-history workloads cannot fit these limits, the gate fails. Do not
lower supported capacity, skip full bootstrap, increase budgets silently, or
activate a narrower product as if it met the requested release. Resolve the
algorithm/retention/resource design with evidence and review first.

Test-only profile: 256 KiB request cap, 16 KiB response cap, one pending/zero queued requests,
1,000 ms **virtual** append deadline. Its immediate clock notifications exercise
closure while a gate remains pending; they are not a real watchdog, memory cap,
deadline benchmark or proof of dashboard responsiveness at maximum history.
